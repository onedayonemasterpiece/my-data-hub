## Причины, которые нельзя смешивать

### 1. Остановка на создании PR

В переданном владельцем продолжении зафиксирован отказ создать PR из-за якобы отсутствующего разрешения именно на публикацию в `my-data-hub`. Там же указано конкретное разрешение владельца на создание и последующее слияние этого исправления после зелёного CI. Передача владельцу ручного Create pull request оставляла задачу незавершённой.

В текущей сессии PR №48 создан тем же штатным GitHub-инструментом в 11:23:30 UTC. Новое ручное подтверждение, другой пользователь, SSH или обход запрещённой операции не потребовались. Значит, постоянная невозможность создать PR в этом репозитории текущими инструментами не подтверждается.

Текущие настройки GitHub отдельно прочитаны через Plugin Management: для этого плагина задано `Allow all actions`, переопределяющее общий режим `Allow low-risk actions`. Настройки не изменялись. Это дополнительное доказательство текущей доступности, но не снимок настроек и входного контекста на момент исторического отказа.

Доступная серверная трасса не доказывает внутреннюю причину исходного автоматического отказа: нельзя утверждать, что reviewer получил конкретное разрешение, или что его механизм теперь исправлен. Установлен сбой продолжения авторизованной работы; точная причина потери/непризнания разрешения остаётся границей расследования.

### 2. Несовпадение исходного дерева и реально исполняемого пакета

Предыдущее восстановление голоса работало из установленного `site-packages/my_data_hub`. Копия `/app/src` внутри старого образа была иной версии. Проверка только checkout, тега или `/app/src` могла принять неверный baseline за исполняемый код и потерять уже работающие восстановление и журналирование при добавлении аналитики.

Исправления восстановления включены ранее в PR №47. PR №48 сохраняет сообщения рабочего обработчика и его INFO logger при настройке uvicorn. Перед текущей выкладкой и после неё проверен именно пакет, разрешаемый Python через `find_spec("my_data_hub")`.

Связанный действующий инцидент: `inc_f077c5784473fd1e3100e1dc`. Его исторический контекст включает исправленную ошибку порядка systemd drop-in (`inc_2586f4fde8253a9383edaa64`) и восстановление после provider 5xx (`inc_51d0857fd6d1b54b4b613e91`). Эти причины отличаются от отказа создать PR.

### 3. Неуспешная задача OpenCode в этой сессии

Задача `dvt_7cb54a314c864e33a65fcb87c6f9dfa3` была запущена в read-only режиме для дополнительного ревью через выбранный владельцем OpenCode. Провайдер `opencode/nemotron-3-ultra-free` завершил её ошибкой `provider_unavailable`: upstream Nvidia ответил 503 «Service temporarily overloaded» до получения содержательного результата.

Это независимый отказ провайдера. Дополнительное агентное ревью не являлось требуемым gate: доступные прямые инструменты позволили проверить diff, дождаться настоящего CI и выполнить уже разрешённую выкладку. OpenCode не использовался для обхода отклонённого действия. SHA256 сохранённого evidence этой задачи: `d475d7c5e6af6b8b050eee809e134a73c8ceb2262cc45cf46271684f49c4e547`.

### 4. Исправленная ошибка привязки операции к работе

Первый вызов rollout в текущей сессии был отвергнут до выполнения с `incident_conflict`: старый source-only `work_ded6e5c4e4acfa87738aac40` не имел incident binding, а вызов содержал явный incident ID. Это ошибка аргументов, а не отказ автоматического согласования.

После `recovery_snapshot` подтверждено отсутствие неопределённых действий и новой запущенной задачи. Создан корректно связанный `work_69b60eadc6e74f7959bcbe67`; та же операция с тем же request key выполнена через тот же шлюз. Никакое ограничение исполнения не ослаблялось.

3. Для продолжаемой работы заполнен существующий delivery contract DevCoveer с кандидатом по image fingerprint. CI и runtime readback закрывают только свои критерии. Новая запись, реальные ответы, финальный документ и подтверждение владельца остаются отдельными открытыми критериями.
4. В `AGENTS.md` добавлен раздел Operational release continuity. Передача работы должна сохранять репозиторий, ветку, точный SHA, согласованные действия, ссылку на решение владельца, IDs work/incident/job и последнее подтверждённое состояние. 5. При отказе сохраняется точная категория и текст. Отказ согласования останавливает соответствующее действие; его нельзя обходить другой учётной записью или каналом. Ошибка схемы/привязки исправляется после readback. Неопределённый результат требует reconciliation. Ошибка необязательного провайдера не делает недоступными остальные разрешённые этапы.

Эти меры исправляют управляемый репозиторий и учёт работы. Они не дают гарантии отсутствия будущих отказов внешнего механизма согласования.

Не сканировать и не перепосылать автоматически старые записи. Не угадывать Slack thread из соседних запросов; конкретный request должен содержать согласованный маршрут.
