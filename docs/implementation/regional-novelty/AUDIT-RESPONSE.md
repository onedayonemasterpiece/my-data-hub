## 2. Решения по находкам

| Находка | Решение и изменение |
|---|---|
| Нет доказанного master с данными | Принято. Сейчас platform.status вернул ABSENT при готовом control plane. Первый этап — настоящий startup/read/save/stop/restore/read. Слово «сохранить существующий master» убрано |
| Две системы checkpoint | Принято. Один действующий owner и один runtime path. Из существующей сборки убрать обязательный broker/verifier/acceptance контур для выбранного цикла; не ставить поверх него RKB journal. Старые данные сначала мигрируются, недостижимый код удаляется после проверки callers |
| Dev journal не нужен пилоту | Принято как рекомендуемый вариант реализации; изменение гарантии остаётся решением владельца. Предложен logical dump/Dataset и восстановление снимка; обещание exact replay всех принятых результатов отозвано |
| Отдельные notebooks и replacement protocol | Принято. PG и обработка в одном notebook. Quota завершает весь сохранённый цикл; новый notebook восстанавливает PG и продолжает pending. Отдельный rotation protocol не нужен для первой карточки |
| Orchestration, updater, 100 ГБ | Принято. SQL pending/unique constraint, один модельный запрос, официальный installer на старте и version в логе. Размер БД измеряется; 100-ГБ приёмка и отдельная update-служба отложены |
| Shared package не используется | Принято. Codec частично извлечён; rotation/releases написаны заново. Они не являются dependency или доказательством reuse. Следующее расширение package происходит после реального совпадения кода у двух consumers; live РКБ не меняется |

## 3. Уточнения, влияющие на правильность решения

### Текущий ABSENT не доказывает всю историю

В этой подготовке наблюдались `control_plane_ready=true`, `master_state=ABSENT`, deployed commit `f7eb3c5f674b772751c815aa055a52f1f52e1828`. Этого достаточно, чтобы требовать первый доказанный цикл с данными. Утверждения «никогда за три месяца», 817 commits и 0 из 266 блогеров здесь не подтверждены независимой проверкой всей истории/импорта; они сохранены как утверждения аудитора. Это не основание откладывать запуск или защищать прежний план.

### Что действительно говорит аудит РКБ

[Аудит от 23.10, A2–A4](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/2cfb2bbf6c95d1ef4efaf5f7871b5e3d559921f5/docs/audits/rkb-complexity-audit-2-20261023.md) прямо предлагает убрать дублирование PG на Dev, перейти на `pg_dump → Dataset → startup restore` и удалить code-пины. Я не учёл этот документ в прежнем плане и сделал сложный текущий контур обязательным донором.

Оценка ~8,9 тыс. строк относится ко всему слою из 31 recovery/snapshot/history/journal файла на срезе 23.10, не только к Dev journal. [Follow-up 25.10](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/2cfb2bbf6c95d1ef4efaf5f7871b5e3d559921f5/docs/audits/rkb-simplification-followup-20261025-opus.md) подтверждает большой spool и расчёт следующего export около 80 MB; это само по себе не доказательство конкретного OOM. [Результат 26.10](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/2cfb2bbf6c95d1ef4efaf5f7871b5e3d559921f5/docs/audits/rkb-simplification-followup2-result-20261026-pro.md) исправил учёт pending без удаления истории. Поэтому предложение аудитора нельзя выдавать за уже внедрённую замену live РКБ.

### Публичный источник не равен сохранённым данным

После внезапной потери notebook snapshot-only возвращает последний подтверждённый снимок. Публикация после него могла измениться/исчезнуть, а уже полученный ответ модели мог не попасть в Dataset. Повторный fetch и inference возможны только при доступности источника/модели и могут дать другой результат. Формулировка «повторяется один цикл» занижает эту цену.

При плановом STOP полный цикл сохраняется перед остановкой. Если эту границу владелец принимает для пилота, перенос Dev journal действительно не нужен. Это один продуктовый выбор о допустимой потере, а не повторный вопрос владельцу о SQL, миграциях или выборе backup-провайдера.

### Свежий OpenCode уже умеет выбирать официальный installer

Проверены [официальная команда](https://dev.opencode.ai/v2/docs/) и [installer](https://opencode.ai/v2/install). Установка OpenCode 2 использует официальный update endpoint и платформенный пакет. Прежний разрыв GitHub latest/v2 не требует собственного feed/promotion framework. Достаточны обычная установка при старте, отсутствие случайного VERSION pin и запуск проверенного `--version` тем же бинарником. Никакое обновление пользовательских установок этой проверкой не выполнено.

## 4. Ответ на два вопроса аудитора

**Q1 — рекомендую убрать Dev journal из пилота.** Конкретный вариант подготовлен: одна PostgreSQL, согласованный logical dump, current/previous private Dataset, restore и повтор доступного непокрытого хвоста. Владелец ещё не подтвердил допустимость потери несохранённых текстов/ответов; status этого решения — proposed. До решения нельзя выдавать snapshot-only за прежнюю гарантию сохранения каждого принятого результата.

**Q2 — измерять на первом полезном цикле, не ставить сутки ожидания перед карточкой.** Записывать actual model/route/version, входные и успешные посты, причины отказа, длительность, размер PG и исход следующей задачи после fresh start. Суточное наблюдение может продолжить нормальную работу после первого результата. Отдельный 24h benchmark не запущен; постоянную доступность free-маршрута и reset quota не обещаем.
