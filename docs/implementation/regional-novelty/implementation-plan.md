# Реализация MDH: значимое новое и хранение физической базы с WAL

Решение владельца от 04.11.2026 принято. Исходный документ из ветки docs/storage-wal-scheme-20261104 включён в main: [bcd7acfb](https://github.com/onedayonemasterpiece/my-data-hub/commit/bcd7acfb6d0cbe635a90528dc30ed1f22c2f2ae2). [Решения владельца](owner-decisions.md), [схема хранения](STORAGE-BASE-WAL.md), [результаты живых проверок](STORAGE-PREFLIGHT-RESULT.md).

**Ближайший продуктовый результат:** реальная региональная публикация превращается в карточку с объяснением новизны и источником; её опубликованный WAL переживает внезапное исчезновение notebook, а новый Kaggle возвращает ту же карточку через MCP без повторного вызова модели. Затем штатная остановка создаёт одну базовую версию и удаляет прежний временный Dataset.

При проверке control plane был доступен, master_state=ABSENT, deployed_commit=f7eb3c5f674b772751c815aa055a52f1f52e1828. Это наблюдение текущего состояния, не доказательство всей истории проекта. Создание проверочных Dataset и CPU notebook не является запуском master с продуктом.

## 1. Один notebook и длинные рабочие сессии

Один Kaggle notebook содержит PostgreSQL, сбор разрешённых источников и обработку через OpenCode. Существующий лёгкий control plane управляет запуском; MCP использует нынешние resolver/data plane, авторизацию, ограниченные роли и single-writer epoch. PostgreSQL остаётся единственной канонической БД, только в Kaggle.

Цикл сессии: восстановить базу и её WAL → периодически собирать и оценивать публикации → публиковать WAL → перед завершением сохранить физическую базу. Сбор идёт внутри длинной сессии каждые 1–3 часа; продуктовый ориентир свежести — около шести часов. После одного сбора notebook не останавливается. Существующий lifecycle учитывает следующий реальный запланированный сбор при решении о завершении сессии: ожидание не должно обрываться через useful-idle 37 минут. Технические heartbeat не считаются полезной активностью; новый scheduler не нужен.

При исчерпании пригодных бесплатных моделей штатно сохранить базу, остановить старое выполнение и начать свежее, продолжив pending из PostgreSQL. Provider keys/auth OpenCode по умолчанию не наследуются. Новый notebook не доказывает новую provider/account quota; причины отказов фиксируются на полезной работе.

Независимые executors, stage orchestration, новый WSS protocol/controller и обязательная библиотека kaggle-runtime не предшествуют первой карточке. Общий код выделяется при реальном повторном использовании.

## 2. Физическая базовая копия + штатный WAL: принятое хранение

Полный контракт — [STORAGE-BASE-WAL.md](STORAGE-BASE-WAL.md). Он заменяет прежние snapshot-only и logical dump. Дополнительного согласования потери хвоста не требуется; гарантируется восстановление до опубликованного хвоста, а его фактическое отставание видно в MCP.

| Участок | Единственный нормальный путь |
|---|---|
| Основной private Dataset | Полная сжатая физическая база после успешного fast-stop; current/previous references |
| Временный private Dataset | Полный необходимый WAL-хвост выбранной базы, включая штатные timeline history; публикация первоначально раз в 15 минут |
| Старт | Распаковать физическую базу, подготовить её WAL, затем запустить PostgreSQL; после завершения recovery — migrations/roles/epoch/MCP |
| Штатная остановка | Прекратить работу → fast-stop PostgreSQL → упаковать PGDATA → создать основную версию → дождаться ready → удалить временный Dataset |
| Рост хвоста | Редкая online pg_basebackup; current reference переключается только на готовые новую базу и её хвост. До переключения restore выбирает прежнюю пару; WAL за время загрузки сохраняется |
| Владелец публикации | Один существующий компонент checkpoints/control plane публикует оба Dataset; второй publisher и Dev journal не создаются |

П1 уже показала замену набора файлов Dataset: каждая версия временного Dataset включает весь необходимый хвост. П2 подтвердила удаление через API. Передачи 100 МБ / 1 ГБ / 10 ГБ измерены; фактическая вместимость ~100 ГБ и квоты остаются в П3; сведения о запущенном CPU notebook и документированном лимите сессии — в П4. Точные результаты и ограничения находятся в [протоколе](STORAGE-PREFLIGHT-RESULT.md). Замеры 100 МБ/1 ГБ/10 ГБ не подменяются временем публикации крошечного тестового файла.

**Порядок изменения существующего кода:**

1. Сохранить физический порядок MasterBootstrap. В существующем PostgresConfig включить archive/recovery параметры так, чтобы write_configuration не затёр их; готовность к записи и время recovery обрабатывать в нынешнем supervisor.
2. В нынешнем notebook entrypoint перенести cold base на момент после успешной остановки PG. Оставить один storage owner, потоковую передачу файлов из Kaggle и штатное сверение ожидаемой версии при потерянном ответе.
3. Удалить второй полный pg_dump из ArchiveCreator вместе с требованиями logical-файла в manifest/provider mapping. Сохранить pg_basebackup для online base. Не объявлять новый формат старым v1 и не терять ранее опубликованные physical checkpoints: сначала восстановить существующие данные их reader в Kaggle, затем сохранить новую физическую базу.
4. Отсоединить обязательные verifier/acceptance notebooks от обычного сохранения. Сохранить используемый потоковый upload из brokered_upload; удалить недостижимые orchestration-функции и их тесты после проверки callers. Не удалять transport вместе с прежним verifier.

Нельзя стартовать пустую БД поверх существующих Dataset только из-за ABSENT. Нельзя добавлять собственные WAL-хэши, payload journal или проверочный notebook на каждое сохранение. Все таблицы, результаты моделей и миграции покрывает штатный PostgreSQL WAL.

Объём до ~100 ГБ — требование к этой схеме сразу, без отдельного упрощённого storage для пилота. П3 должна подтвердить размещение PGDATA, архива и WAL, квоту и передачу: измеренный /kaggle/working около 21 ГБ для этого недостаточен. Выбрать и проверить Kaggle scratch в существующей конфигурации путей; Dev не становится местом БД. Внешние копии на диск/другое облако остаются вне текущего объёма.

## 3. Один источник, SQL-очередь, одна оценка публикации

Начать с одного уже разрешённого сайта/ленты региона со стабильными URL. Не открывать новый discovery и не ждать подключения TG/VK. Full source revision сохраняется до вызова модели. Редактирование поста создаёт новую revision; повтор тех же source/post/revision исключается unique constraint.

Новая предметная миграция добавляет только недостающие полную revision, её cursor и результат; конкретная форма приведена в [novelty-implementation.md](novelty-implementation.md). Pending выбираются SQL по отсутствующему результату и допустимому времени следующей попытки. Один последовательный notebook loop не требует межпроцессных leases, stage_run, worker_result_inbox и нового workflow engine.

Нормальный путь — один модельный запрос на новую revision. В него входят полный материал и релевантное прошлое из SQL/FTS. Модель одновременно возвращает: что изменилось, почему это значимо для региона, время/объект, source evidence и связь с прежним. Отдельные extract/judge/writer вызовы не создаются. Полный ответ сохраняется в PG.

Полный текст и offsets чанков не обрезаются ради encoder/model лимита. Если материал не помещается в доступный контекст, он остаётся сохранённым и отмеченным как необработанный; используется подходящий разрешённый маршрут, а другие посты продолжают обрабатываться. Техническая ошибка не превращается в «нового нет». BGE и отдельные embedding workers следуют после первой карточки, когда будет конкретная потребность улучшить поиск.

MCP даёт `novelty.list`, `novelty.get` и состояние coverage: источник/время, что нового, сравнение с прежним, ссылки; отдельные capture/analysis lag и непроанализированный хвост. Репост известного факта не считается независимым подтверждением. Интерфейс не требует от владельца SQL или ручного управления notebook.

## 4. Свежий OpenCode обычной установкой

На каждом старте нового notebook использовать официальный текущий installer OpenCode 2 и запускать установленный им бинарник. В bootstrap достаточно:

```bash
set -euo pipefail
curl -fsSL https://opencode.ai/v2/install | env -u VERSION bash -s -- --no-modify-path
"$HOME/.opencode/bin/opencode" --version
```

`VERSION` удаляется только из среды установщика, чтобы случайный старый pin не отменил свежую установку. Установщик сам получает актуальную версию через официальный update endpoint. В журнал цикла записывается фактическая версия; рабочая команда использует тот же абсолютный путь. Отдельные release feed, promotion/canary service и SHA-пины бинарника не нужны. Это описание будущего bootstrap, не сообщение о выполненной установке.

Provider keys/auth не наследуются из предыдущего notebook. При обязательном ключе используется только явно заданная владельцем привязка. Kaggle control credentials и transport auth сохраняют собственные роли. Источники: [официальная установка](https://dev.opencode.ai/v2/docs/), [installer](https://opencode.ai/v2/install), [CLI](https://dev.opencode.ai/v2/docs/cli/commands/).

## 5. Замер доступности на полезной работе

Первую карточку не откладывать на сутки. В обычный цикл включить уже доступные execution logs: run ID, OpenCode version, фактические provider/model, число входных/успешных постов, ошибки по причинам, время и длительность, размер PG через `pg_database_size`.

Если возникнет quota refusal, сохранить цикл, остановить старый execution и записать результат следующей настоящей задачи в fresh окружении. Это измеряет доступность; наличие новой среды само по себе не означает новую квоту. Объявленный provider cooldown учитывается, бесконечный цикл запусков не создаётся. Суточное наблюдение может продолжить обычную работу после первого результата. Отдельный 24-часовой benchmark этим документом не запускается.

Схема хранения проектируется для объёма до ~100 ГБ сразу. П3 проверяет ограничения, время передачи и рабочее место; прохождение маленькой продуктовой приёмки само по себе не доказывает ёмкость 100 ГБ. Внешние backup copies отложены. Размер PG, WAL и длительность публикации измеряются в обычном цикле.

## 6. Порядок исполнения и продуктовая приёмка

1. **Живые П1–П4 до storage-кода:** сохранённые результаты П1/П2 повторять не нужно. Не повторять успешный ряд передач до 10 ГБ; завершить проверку квот и конкретного размещения данных; документированный лимит не выдавать за 12-часовой опыт.
2. **Один lifecycle с данными:** physical base + native WAL через существующие PG/start/publisher primitives; три теста реального PG18.4 + pgvector0.8.6 из STORAGE-BASE-WAL. Сохранить читаемость нужных старых checkpoints.
3. **Настоящий источник и первая карточка:** полный post revision, атомарный cursor, один модельный результат, novelty.list/get с объяснением и ссылкой. Повтор capture не создаёт дубль.
4. **Аварийная приёмка:** карточка создана и её WAL опубликован → notebook убит без STOP → новый notebook восстанавливает base + WAL → та же revision и тот же ответ читаются через штатный MCP без нового inference.
5. **Штатная приёмка:** STOP → одна готовая базовая версия → старый временный Dataset удалён → следующий старт возвращает ту же карточку без внешнего хвоста этой базы.
6. **Расширение полезности:** больше источников, BGE и качество поиска по фактической потребности; общая библиотека при втором потребителе того же кода.

Evidence включает исходный пост, сохранённую карточку, конкретные base/WAL версии и чтение после нового выполнения. HTTP200, unit tests и наличие документа не заменяют этот результат. В текущей интеграции runtime-код не изменён; выполненные проверки отделены от ещё не проведённой продуктовой приёмки.

## 7. Общее переиспользование без обязательного framework

`kaggle-runtime` остаётся созданным репозиторием. Только codec был частично извлечён из РКБ; rotation/releases — новые неиспользуемые политики, не доказанный перенос. Они не являются зависимостью первого продукта и не задают обязательную архитектуру.

Сначала использовать работающие primitives и существующие owners MDH. При появлении второго consumer извлечь совпавший нейтральный provider/transport/bootstrap код в общий package и удалить заменённые локальные функции. Не копировать монолит РКБ, не менять его live и не начинать вторую checkpoint-машинерию. Эта последовательность сохраняет требование владельца о reuse и приближает первый продукт.
