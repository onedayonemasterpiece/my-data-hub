## 1. Решение владельца

Слова владельца, 04.11.2026, в пересказе:

- Основной Dataset с БД — версионируемое хранилище. Нужны **сотни версий за долгий срок, а не тысячи**: примерно одна версия на запуск Kaggle. При штатной остановке версия сохраняется всегда.
- Частые сохранения изменений идут во **временный Dataset**. Он живёт, пока работает Kaggle, и удаляется после сохранения основного.
- Если Kaggle умер, временный Dataset остаётся. При восстановлении его более свежие изменения применяются поверх соответствующей базовой копии.
- **Не делить на пилот и «потом».** Целевой рабочий объём — до ~100 ГБ; возможность разместить и сохранить его подтверждает П3.

Snapshot-only и перенос Dev journal больше не рассматриваются.

## 2. Схема

Штатный механизм PostgreSQL: полная физическая базовая копия + архив WAL. Существующая версия runtime сохраняется: **PostgreSQL 18.4 + pgvector 0.8.6**. Собственный формат изменений, журнал команд, хэш-цепочки и проверочные notebook не создаются.

| Где | Что лежит | Когда пишется |
|---|---|---|
| Основной private Dataset | Сжатая полная физическая копия PGDATA + `base.json`: `base_id`, версии PG/pgvector, время | Новая версия при штатной остановке и по §2.4 |
| Временный private Dataset `<основной>-wal-<base_id>` | Полный накопленный хвост штатных WAL-файлов и `.history` для базы + `wal.json` только с `base_id` | Новая версия раз в N минут; начально N = 15; уточнить на настоящем WAL |
| Dev | Никаких данных БД или WAL. Только существующее состояние запуска в control plane | — |

### 2.1 Во время работы

- В существующем генераторе конфигурации: `wal_level=replica`, `archive_mode=on`, `archive_command` копирует штатные файлы в локальный каталог, `archive_timeout=300s`. Сохранить штатные `fsync` и `full_page_writes`.
- П1 показала: новая версия Dataset **не наследует** не загруженные в неё файлы. Поэтому каждая версия временного Dataset содержит весь необходимый хвост текущей базы, а не только новые сегменты.
- Учитывая ограничение Kaggle на число файлов, хвост передаётся одним сжатым tar-контейнером с непрозрачным именем `wal.blob`: внутри неизменённые WAL и `.history`. Это упаковка для транспорта, не новый формат журнала или WAL-manifest. Непрозрачное имя использует существующий provider_storage подход MDH, не добавляет отдельный формат журнала.
- `archive_command` возвращает успех только после завершения локальной копии; publisher не подбирает ещё копируемые файлы. Успех локального архивирования не означает сохранение в Dataset.
- PostgreSQL обеспечивает штатные проверки записей WAL. Повторные хэши и проверочные прогоны на каждое сохранение не добавляются. CRC не доказывает полноту опубликованного хвоста; publisher сохраняет непрерывный набор нужных файлов.

### 2.2 Плановая остановка (STOP, исчерпание квоты моделей, лимит сессии)

1. Прекратить новую работу. Дождаться успешного `pg_ctl stop -m fast`; только затем упаковать согласованный кластер.
2. Включить **весь PGDATA, в том числе `pg_wal`**. Для открытия этой холодной копии внешний WAL не требуется; это не разрешает удалять внутренний `pg_wal` или пропускать данные внешних tablespaces, если они используются.
3. Опубликовать новую версию основного Dataset. Сначала сохранить ожидаемую версию в существующем состоянии публикации. При потерянном ответе сверить эту же версию штатным API, не создавать следующую вслепую.
4. Дождаться Kaggle `ready` — единственная внешняя проверка сохранения. Зафиксировать новую самодостаточную холодную базу в существующей current reference; только после этого удалить временный Dataset прежней базы. При ошибке публикации прежний Dataset сохраняется.

### 2.3 Старт

1. Взять основную версию из существующей current reference и распаковать PGDATA до старта PostgreSQL: существующие фазы `RESTORING` → `STARTING_POSTGRES`. Ссылка выбирает готовую холодную базу либо завершённую пару online-база + её WAL; просто самая новая версия Dataset может быть ещё не переключённым кандидатом (§2.4).
2. Если существует временный Dataset с тем же `base_id`, скачать полный хвост, подготовить `restore_command` и `recovery.signal`. Исключить унаследованный `standby.signal` и прежние ограничения `recovery_target*`; используется штатный выбор последней доступной timeline.
3. Конфигурация восстановления должна пережить существующий `write_configuration()`, полностью перезаписывающий `postgresql.auto.conf`: параметры задаются через тот же генератор. `restore_command` возвращает ненулевой код при отсутствии файла, поддерживает сегменты и `.history`.
4. Запустить PG; в существующем механизме готовности дождаться завершения recovery и возможности записи, затем выполнять migrations/roles/epoch/MCP. Учитывать время реального восстановления в существующем timeout; один `pg_isready` не заменяет проверку выхода из recovery.
5. Конец доступного WAL может штатно выглядеть как отсутствие следующего файла. Это не доказательство сохранности непубликовавшихся транзакций. Новая timeline после recovery и её `.history` входят в последующие публикации того же хвоста.
6. WAL с чужим `base_id` не применять. Сначала окончательно выбрать восстановленную базу, затем удалять временные Dataset, которые к ней не относятся; не уничтожать возможный хвост предыдущей базы до попытки fallback.
7. Если текущая база не стартует, взять предыдущую основную версию. WAL отвергнутой текущей базы к ней не применять. Если обе не стартуют — ошибка запуска, без подстановки пустой БД.

Временный Dataset аварийного запуска остаётся до следующей успешно сохранённой базовой версии. Автоматический fallback на предыдущую базу означает более старые данные; статус MCP отражает фактически выбранную версию.

### 2.4 Одно правило против разрастания хвоста

Если публикация полного WAL-хвоста занимает дольше нескольких минут, выполнить онлайн `pg_basebackup --wal-method=stream`. Начальный ориентир порога — 3 минуты; его уточняет П3 и длительность публикаций настоящего WAL. Не ждать, пока загрузка превысит весь интервал N. Основной Dataset получает редкую дополнительную версию. Других правил ротации нет.

До переключения `base_id` сохранять старую базу A с её хвостом. Новая копия B включает WAL для собственной согласованности, но записи продолжаются во время загрузки: хвост B должен включать нужные сегменты от границы копии и записи за время публикации. Не обнулять хвост по времени получения `ready`. Готовность B сама по себе не меняет существующую current reference: переключить её только после готовности B и относящегося к ней накопленного хвоста. При аварии до переключения восстановление по-прежнему выбирает A + WAL-A. После переключения можно удалить прежний временный Dataset. Использовать существующую current/previous reference и штатные границы PostgreSQL, без нового журнала, manifest или framework.

### 2.5 Частота версий основного Dataset

Число версий — число завершённых запусков плюс редкие версии §2.4. Notebook живёт **длинными сессиями**; сбор источников идёт внутри сессии по расписанию, ориентир свежести — 6 ч. Короткие циклы «запустил → собрал → остановил» не использовать. Существующий lifecycle учитывает следующий реальный запланированный сбор при решении о завершении сессии: ожидание сбора через 1–3 часа не должно обрываться через useful-idle 37 минут. Технический heartbeat не становится полезной активностью. Это изменение согласуется с принятым требованием длинных сессий в существующем lifecycle, без нового scheduler. По П4 посчитать ожидаемое число версий в год.

### 2.6 Потеря при аварии

При штатной публикации ориентир отставания — `archive_timeout + N + время загрузки и обработки Dataset`. Значение 15–20 мин без времени загрузки не является строгой верхней границей. При ошибке или отставании publisher окно потери растёт. Локальный WAL утрачен вместе с kernel, если ещё не попал в готовую внешнюю версию.

MCP показывает фактическую последнюю готовую версию базы/WAL, время её публикации и текущее отставание публикации. Время создания Dataset не выдавать за время последней сохранённой транзакции. Никаких новых блокирующих статусов, требующих человека.

Подробные receipts, точные байты, источники лимитов и оставшиеся измерения: [STORAGE-PREFLIGHT-RESULT.md](STORAGE-PREFLIGHT-RESULT.md). Рабочие ~100 ГБ нельзя размещать в измеренном ~21-ГБ /kaggle/working; Kaggle scratch выбирается и проверяется в существующей конфигурации путей. Видимые statvfs байты не доказывают выделенную квоту.

## 6. Ровно три различающие проверки

На реальной **PG18.4 + pgvector0.8.6** в изолированном CI, без подделки PostgreSQL:

1. Запись строки/вектора → завершённый архивный WAL → kill без STOP → restore базы + WAL: запись есть; без внешнего WAL её нет. Повторный аварийный цикл внутри этого сценария проверяет новую timeline и `.history`.
2. Временный WAL с чужим `base_id` не применяется, даже если физически происходит из того же кластера.
3. Плановая остановка → новая холодная база → временный Dataset удалён → старт без внешнего WAL читает те же данные.

Живая приёмка вместе с первой карточкой: карточка создана, её WAL вошёл в готовую внешнюю версию → kill → новый notebook → та же карточка читается через MCP без повторного вызова модели. Затем STOP → одна новая основная версия, временного Dataset нет.
