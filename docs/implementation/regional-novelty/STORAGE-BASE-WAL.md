## 1. Решение владельца

Слова владельца, 04.11.2026, в пересказе:

- Основной Dataset с БД — версионируемое хранилище. Его нельзя забивать тысячами мелких копий. Нужны **сотни версий за долгий срок, а не тысячи**: примерно одна версия на запуск Kaggle. При остановке Kaggle версия сохраняется всегда.
- Частые сохранения, а лучше только изменения, идут во **временный Dataset**. Он живёт, пока работает Kaggle, и удаляется после сохранения основного.
- Если Kaggle умер, временный Dataset остаётся. Восстановление идёт сначала с него как с более актуального.
- **Не делить на пилот и «потом».** Схема сразу рассчитана на рабочий объём до ~100 ГБ, чтобы её не переделывать.

Snapshot-only и перенос Dev journal больше не рассматриваются.

## 2. Схема

Используется штатный механизм PostgreSQL: физическая базовая копия + архив WAL (восстановление по журналу, PITR). Собственный формат изменений, журнал команд, хэш-цепочки и проверочные notebook не создаются.

| Где | Что лежит | Когда пишется |
|---|---|---|
| Основной private Dataset | Сжатая физическая базовая копия PGDATA (tar) + маленький `base.json`: id базы, версия PG/pgvector, время | Новая версия при каждой остановке Kaggle и при правиле из §2.4 |
| Временный private Dataset `<основной>-wal-<base_id>` | Сегменты WAL, накопленные после этой базы, + `wal.json` с `base_id` | Новая версия раз в N минут (стартовое значение 10–15) |
| Dev | Ничего из данных. Только то, что control plane уже хранит о запуске | — |

### 2.1 Во время работы

- В `postgresql.conf` notebook: `wal_level=replica`, `archive_mode=on`, `archive_command` копирует сегмент в локальный каталог архива, `archive_timeout` (стартовое значение 300 с).
- Раз в N минут новые сегменты публикуются версией временного Dataset. Как именно — зависит от проверки П1 в §3.
- Postgres сам гарантирует, что в архив попадают только завершённые сегменты. Повторно их не проверять.

### 2.2 Плановая остановка (STOP, исчерпание квоты моделей, приближение к лимиту сессии)

1. Прекратить новую работу. Штатно остановить PG (`pg_ctl stop -m fast`): это даёт согласованный PGDATA без отдельного WAL.
2. Упаковать PGDATA со сжатием и опубликовать новую версию основного Dataset. Сначала записать, какую версию ожидаем. Если ответ потерян, сверить ту же версию штатным API, а не создавать следующую вслепую.
3. Дождаться готовности версии (статус Kaggle `ready`). Это единственная внешняя проверка. После неё удалить временный Dataset прежней базы.

### 2.3 Старт

1. Взять последнюю готовую версию основного Dataset и распаковать в PGDATA. Это уже нынешний порядок `MasterBootstrap`: restore **до** старта PG, см. `master_runtime/bootstrap.py` (`RESTORING` → `STARTING_POSTGRES`).
2. Если существует временный Dataset с тем же `base_id`, скачать его сегменты, прописать `restore_command` на этот каталог и создать `recovery.signal`.
3. Запустить PG. Он сам проиграет WAL до конца и откроется для записи. Затем обычные migrations/roles/epoch/MCP.
4. Временные Dataset с чужим `base_id` (от более старой базы) не применяются и удаляются.
5. Если текущая база не стартует, взять предыдущую версию основного Dataset. Временный WAL к ней не применяется: он от другой базы. Если не стартуют обе, это ошибка запуска. Пустая БД поверх существующих данных не подставляется.

Временный Dataset умершего запуска применяется на следующем старте и удаляется после следующей базовой версии по §2.2.3.

### 2.4 Одно правило против разрастания хвоста

Если WAL текущей базы вырос так, что его публикация заметно дольше интервала N, во время работы делается внеочередная базовая копия (`pg_basebackup`, без остановки PG). Порог выбирается по замеру П3. Основной Dataset получает редкую дополнительную версию, хвост снова короткий. Других правил ротации нет.

### 2.5 Частота версий основного Dataset

Число версий равно числу запусков Kaggle (плюс редкие версии по §2.4). Поэтому notebook должен жить **длинными сессиями**: сбор источников идёт внутри сессии по расписанию (ориентир свежести — 6 ч). Нельзя делать короткие циклы «запустил → собрал → остановил»: при таком расписании за год набегут тысячи версий. Если useful-idle 37 мин останавливает notebook между сборами, плановый сбор считается полезной активностью. По замеру П4 посчитать ожидаемое число версий в год и указать его в PR.

### 2.6 Потеря при аварии

Не больше `archive_timeout` + N минут работы, то есть порядка 15–20 мин при стартовых значениях. Эта граница указывается в статусе MCP: время последней опубликованной версии WAL/базы.

## 4. Что переиспользовать и что удалить

| Код | Действие |
|---|---|
| `master_runtime/postgres.py` (`start`, `stop`, инструменты PG) | Использовать. Добавить параметры архива WAL и восстановления в существующую генерацию конфигурации |
| `master_runtime/bootstrap.py` | Порядок оставить. Restore = распаковка базы + подготовка WAL-восстановления |
| `checkpoints/archive.py` `ArchiveCreator` | Оставить `pg_basebackup` для §2.4. **Удалить второй полный `pg_dump`**, который сейчас делается на каждом checkpoint: это вторая копия той же базы |
| `checkpoints/kaggle_runtime.py`, `publisher.py`, `control_plane/runtime.py` | Один публикующий компонент для основного и временного Dataset. Двух владельцев публикации быть не должно |
| `checkpoints/brokered_upload.py`, `acceptance*.py`, `verifier*.py`, `restore_probe.py`, `acceptance/checkpoint_launcher.py` | Отсоединить от обычного цикла. Код, ставший недостижимым, удалить вместе с тестами после проверки callers |

Логический `pg_restore` из прежней редакции плана не делать. На 100 ГБ он пересобирает индексы часами, и ему нужен другой порядок запуска.

## 5. Запрещено в этой задаче

- Свой формат изменений, выгрузка строк по меткам, журнал команд на Dev или в Kaggle.
- Хэши/SHA сегментов WAL и базы поверх контрольных сумм PostgreSQL и статуса готовности Kaggle; отдельный verifier notebook или restore drill на каждом сохранении.
- Новые статусы вида `unknown`/`needs_review`, ожидающие человека. Потерянный ответ публикации сверяется по ожидаемой версии.
- Удаление временного Dataset до готовности новой базовой версии.
- Изменение live РКБ.

## 6. Различающие проверки

Все проверки — на реальной PG17 + pgvector в CI, без подделки PostgreSQL:

1. Запись → архив WAL → «смерть» (kill без остановки) → восстановление базы + WAL → запись на месте. Без WAL её нет.
2. Временный WAL с чужим `base_id` не применяется.
3. Плановая остановка → новая база → временный удалён → старт без WAL читает те же данные.

Живая приёмка вместе с первой карточкой: карточка создана → notebook убит без STOP → новый notebook поднимается с базы + временного WAL → та же карточка читается через MCP без повторного вызова модели. Затем плановая остановка → в основном Dataset одна новая версия, временного нет.
