# Решения владельца: My Data Hub и общий Kaggle runtime

Дата: 4 ноября 2026, Europe/Kaliningrad. Источник: текущая беседа ChatGPT, ответ владельца после комплексного анализа. Ссылка на приватную беседу не предоставлена. Этот документ фиксирует новые прямые указания владельца и заменяет открытые вопросы раздела 11 первоначального исследования.

## 1. Продуктовый результат

Первый продукт — **значимое новое в Калининградской области**: система сама получает публикации из выбранных источников, сохраняет их, сопоставляет с уже известным и выдаёт обоснованную подборку новых общественно значимых изменений со ссылками. Цель свежести из исходного задания — примерно шесть часов. Владелец не должен работать с SQL, миграциями, checkpoint или инфраструктурными параметрами.

Тренды, мнения гостей, история людей/организаций/реальных проектов и POI остаются требованиями следующего развития. Корпус с первого этапа сохраняет полезные несобытийные материалы; схема не замыкается на event-only фильтре.

## 2. Исчерпание бесплатных моделей

Решение владельца: остановить данный Kaggle executor и запустить свежий. По умолчанию не переносить в него OpenCode API keys, auth.json, домашнюю конфигурацию и credentials прошлого исполнителя. Если конкретному разрешённому провайдеру ключ обязателен, использовать несколько заранее настроенных владельцем credential aliases; секрет передаётся только конкретному процессу/задаче, не журналируется и не попадает в Dataset или репозиторий.

Это выбранный штатный путь восстановления доступности. Гипотеза «в новом окружении часть моделей снова заработает» сохраняется как проверяемая; создание notebook само по себе не является доказательством новой квоты. После запуска требуется проверить пригодность хотя бы одного разрешённого free маршрута для нужной роли. Достоверный provider/account cooldown учитывается; ошибки credentials, transport и конфигурации не переименовываются в исчерпание квоты.

Порядок: сохранить уже полученное через owning ingress/journal → прекратить выдачу новой работы старому executor → запросить STOP → подтвердить окончание конкретного provider execution → создать новый execution с новой generation и чистым OpenCode auth context → продолжить незавершённое. Потерянный ответ на STOP/start автоматически сверяется по исходному operation key, без участия владельца и без второго слепого запуска.

Начальный профиль использует отдельный PG master и сменяемые OpenCode executors. Поэтому квота модели не заставляет перезапускать базу. Если будущий профиль совмещает их в одном notebook, общий planned-stop путь обязан завершить RKB checkpoint/ownership handover до остановки. Это условие корректности совмещённого профиля, не новый продуктовый вопрос.

Если свежая среда снова не даёт пригодной модели, controller продолжает управляемое восстановление в рамках существующего provider admission и доступной ёмкости; не создаёт параллельные дубликаты и не теряет очередь. Повторный отказ классифицируется и получает следующий разрешённый момент запуска. Платный fallback этим решением не выбран.

## 3. Сохранение как в РКБ

Результат должен переживать исчезновение Kaggle. Используется существующая схема РКБ: exact command в ограниченном Dev journal/spool, канонический PostgreSQL в Kaggle, пакетный verified Dataset checkpoint и replay точного хвоста после восстановления. Dataset не обновляется после каждой строки, поста или токена.

Уточнение по коду: в РКБ Dev journal содержит точные payload/outcome bytes; это не только metadata. Он переживает потерю kernel при сохранности Dev диска. Dataset Saved появляется только после native readback и покрытия конкретной операции. Действующая policy запуска checkpoint: quiet 15 минут, интервал 30 минут и planned stop. Эти числа описывают инициацию, а не гарантированную длительность upload.

Перенос в MDH оформляется ADR: PostgreSQL остаётся единственной канонической бизнес-БД; Dev не хранит PGDATA, не обслуживает поиск по spool и не становится второй бизнес-базой. В существующей control SQLite допускается ограниченный неканонический журнал replay. Дополнительный receipt service не создаётся.

Подробный разбор и расхождение старой документации с кодом находятся в [приложении РКБ](rkb-storage-evidence.md). Одновременная потеря kernel и ещё не покрытого Dataset Dev journal — отдельная граница имеющейся схемы, не обещание полного disaster recovery.

## 4. SQL и миграции

Владельцу нужен готовый продукт. SQL, DDL, схема, хранимые процедуры и миграции — обязанности реализации. Нормальный пользовательский путь не требует выбора роли SQL или ручной миграции. Generic SQL не добавляется в публичный продуктовый MCP; приложение использует типизированный ingress и предметные чтения. Версионированные миграции применяет компонент развёртывания под соответствующей служебной ролью.

## 5. Объём и внешние копии

Ориентир **менее 100 ГБ относится к активной базе с её индексами и данными**. Основной механизм постоянства — Kaggle Dataset. Внешние копии на диск или другое облако возможны позже; они **не входят в текущий проект**, бюджет базы и критерий первого продукта. Не проектировать сейчас отдельный backup service, расписание копий или облачное хранилище.

100 ГБ — верхний продуктовый ориентир, не размер первого пилота и не заявленная текущая ёмкость РКБ. У донора обнаружены ограничения archive 8 GiB / unpacked 16 GiB / recovery 900 секунд. Их нужно согласованно параметризовать и проверять на фактическом рабочем наборе; нельзя обещать восстановление 100 ГБ после изменения одной константы. Нынешний snapshot — полный physical PG capture, не найденный incremental upload.

Полный смысловой текст и evidence сохраняются; изображения представлены ссылками. Старые технические traces и производные промежуточные файлы не обязаны бесконечно занимать активную БД. Политика очистки не удаляет единственный непокрытый journal или исходный текст ради прохождения лимита.

## 6. Общий код и постоянная актуальность OpenCode

Создан отдельный приватный репозиторий `onedayonemasterpiece/kaggle-runtime`. Он является владельцем извлекаемого нейтрального кода Kaggle/WSS/lifecycle/executor. Продукты подключают версии общего пакета, держат предметные адаптеры и самостоятельные controllers. Модель Live/Миры служит образцом такой организации; audio-протокол не переносится в jobs.

OpenCode обновляется регулярно во всех исполняемых окружениях. Конкретная версия закрепляется на attempt; свежие совместимые stable-релизы получают новые attempts, долгоживущие процессы проходят управляемую активацию. Новая major обнаруживается отдельно, старое значение GitHub latest не считается достаточной проверкой. Появление новой версии на диске не означает обновление работающего процесса. Подробная инженерная policy — в проекте реализации.

Из прежнего голоса сохраняется полезное окно **37 минут для MDH**. Аудит установил у РКБ фактический useful-idle 1800 секунд; в MDH это явный профиль `useful_idle_seconds=2220` поверх того же механизма. Heartbeat не продлевает полезный спрос. Ни одно из этих значений не является интервалом Dataset checkpoint.
