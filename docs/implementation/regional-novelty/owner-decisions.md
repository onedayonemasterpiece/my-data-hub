# Принятые решения владельца

Источник — прямые поручения и ответы владельца, включая переданный 04.11.2026 документ [STORAGE-BASE-WAL.md](STORAGE-BASE-WAL.md). Его исходная редакция bcd7acfb включена в main. Вопрос о выборе хранения закрыт; повторного подтверждения snapshot-only не требуется.

## Продукт

- Первым результатом служит значимое новое в Калининградской области, с объяснением изменения и источниками; ориентир свежести — около шести часов.
- Полные публикации и ответы моделей сохраняются. Пользователю не нужны SQL, миграции или ручное управление notebook — это обязанности реализации.
- Один notebook содержит PostgreSQL и обработку. Полные revisions, SQL pending/unique constraints и одна оценка поста остаются основой.
- OpenCode устанавливается актуальным официальным installer на каждом старте; фактическая версия записывается в лог.
- При исчерпании пригодных бесплатных моделей выполняется штатное сохранение и остановка Kaggle, затем свежий запуск. OpenCode provider keys/auth по умолчанию не передаются; обязательные ключи задаются только явными привязками. Новая среда не объявляется гарантией сброса квоты провайдера.

## Хранение — принято, без деления на пилот и потом

- **Основной private Dataset:** полная сжатая физическая копия PGDATA при штатной остановке. Не pg_dump. Сохраняются current/previous references.
- **Временный private Dataset:** штатный WAL соответствующей базы; публикация ориентировочно каждые 10–15 минут, archive_timeout первоначально 300 секунд. Фактические интервалы уточняются по замерам, а не считаются доказанным SLA.
- **Старт:** распаковать выбранную базу, применить её опубликованный WAL штатным recovery PostgreSQL и открыть существующий MCP path.
- **Удаление временного Dataset:** после готовности новой основной версии; при online смене базы также сохранить нужный новый хвост. При аварии временный Dataset остаётся для следующего запуска.
- **Один publisher** публикует оба Dataset. На Dev не хранится PGDATA/WAL/канонические данные. Собственный журнал команд и verifier notebook на каждое сохранение не нужны.
- **До ~100 ГБ:** схема учитывает этот рабочий объём сразу. Возможность размещения и публикации должна быть измерена. Внешние backup copies пока не входят в задачу.
- **Длинные сессии:** сбор происходит внутри работающего notebook. Одна основная версия на штатно завершённую сессию, плюс редкие базы при разрастании WAL. Ориентир — сотни основных версий за долгий срок; короткие сбор/STOP циклы не применяются. Плановый сбор учитывается useful-idle правилом 37 минут.

Граница аварийной сохранности — база, зафиксированная существующей current reference, и её полный опубликованный WAL. Online-кандидат становится current после готовности базы и необходимого хвоста; до этого используется прежняя пара. Холодная база после fast-stop самодостаточна и может стать current после ready. Неопубликованные транзакции могут потеряться. 15–20 минут — ориентир при нормальной публикации, к нему прибавляются upload/processing; ошибки публикации увеличивают отставание. MCP показывает фактическую свежесть сохранения. Это не snapshot-only, не обещание сохранности каждого локального COMMIT и не основание снова задавать владельцу закрытый вопрос.

## Переиспользование

Общие решения Kaggle/WSS нужно выявлять и выносить в общий код при реальном повторном использовании. Репозиторий kaggle-runtime уже создан; его неиспользуемые новые политики не становятся обязательным этапом. Использовать нынешний provider и streaming transport MDH; не создавать второго владельца публикации. Live РКБ не изменяется в этой задаче.

## Что отменено и что ещё предстоит измерить

Прежние обязательные Dev recovery journal, независимые executor notebooks, release feed/promotion/pins OpenCode и внедрение двух consumers до карточки были решениями автора старого плана. Они отозваны. Позднейшее предложение logical snapshot-only с короткими циклами заменено принятой физической базой с WAL.

Суточный замер бесплатных моделей не является предварительным этапом первой карточки и отдельно не запущен. Доступность измеряется на полезной работе; никакой новой гарантии бесплатных квот не дано.

Открыты инженерные измерения, а не выбор владельца: крупная передача/квоты/место и runtime recovery. Статусы — в [STORAGE-PREFLIGHT-RESULT.md](STORAGE-PREFLIGHT-RESULT.md), следующий исполнительский порядок — в [implementation-plan.md](implementation-plan.md).
