# Решения владельца и граница пересмотра после аудита

04.11.2026. Источник — прямые поручения и ответы владельца в этой беседе. Пересланный CHANGES_REQUIRED — внешняя оценка, не автоматическое согласие владельца со всеми предложениями аудитора.

## Обязательные решения, которые сохраняются

- Первый продукт — значимое новое в Калининградской области, ориентир свежести около шести часов, объяснение изменения и ссылки на источники.
- При исчерпании пригодных бесплатных моделей завершать данный Kaggle и начинать свежий; не переносить OpenCode provider keys/auth по умолчанию. Обязательные ключи — только явно настроенные привязки.
- Результат должен переживать исчезновение Kaggle; основная постоянная копия — Dataset, без upload каждой записи.
- SQL, миграции и эксплуатационная реализация — обязанности инженеров. Пользователь получает продукт.
- Менее 100 ГБ — ориентир активной БД с индексами. Внешние backup copies на диск/другое облако отложены.
- OpenCode должен оставаться актуальным.
- Общий Kaggle/WSS код нужно выявлять и переиспользовать. Создание общего репозитория разрешено и выполнено; живая миграция РКБ этим не поручалась.
- Раннее полезное окно MDH 37 минут сохраняется как consumer setting; оно не является частотой Dataset uploads и не требует отдельного worker framework.

## Что было решением автора прежнего плана

Обязательное разделение PG master и OpenCode executors, перенос точного Dev recovery journal, собственный release feed/promotion/pins и adoption двух consumers до первого продукта были проектными решениями ChatGPT. Они не должны приписываться владельцу. Эти обязательные условия отозваны из пилота после аудита.

Первый предлагаемый путь теперь — один notebook, обычная PG очередь, одна оценка поста, штатный installer OpenCode при старте, Dataset save/restore и первая карточка через MCP. Общий пакет развивается при появлении реального второго потребителя.

## Единственное существенное изменение гарантии, требующее решения

Предлагается не переносить Dev journal, а восстанавливать последний подтверждённый `pg_dump` из Dataset. При плановом завершении цикла сохраняются и тексты, и ответы моделей, и cursor. При внезапной потере notebook ещё не попавший в снимок хвост может потребовать повторного сбора и анализа.

**Повторный сбор не гарантирует прежний результат:** публикация могла измениться/исчезнуть, модель может ответить иначе. Поэтому фразу «повторяется один цикл» нельзя выдавать за отсутствие потери данных. Допустимость такого хвоста владелец пока не подтвердил. Нельзя закрыть это решение как согласованное на основании пересланного вопроса аудитора.

Рекомендация автора исправленного плана: принять snapshot-only для первого пилота с короткими циклами, сохранив явную границу последнего подтверждённого Dataset. До ответа можно выполнять независимую подготовку lifecycle/capture/MCP; нельзя объявлять новую аварийную гарантию принятой.

## Вопрос о суточном замере

Измерять доступность бесплатных моделей нужно на настоящей полезной работе первого пилота: фактический маршрут, число завершённых постов, отказы, длительность и результат после свежего запуска. Не нужно откладывать первую карточку до отдельного 24-часового benchmark.

Отдельный суточный эксперимент сейчас не запущен и не выдан за разрешённый. После первого работающего цикла обычное наблюдение даст исходные данные для выбора частоты и объёма. Новый notebook не объявляется доказательством сброса provider/account quota.
